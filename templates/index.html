About

One job per agent, and nothing taken on trust.

Most AI debugging tools ask a single model to read the error, guess the cause, rewrite the code and declare victory. When it is wrong, nothing catches it.

This project splits that work across specialised agents that hand work to each other like a small team. Each has a narrow prompt and a single responsibility, which makes it easier to keep reliable and easier to test on its own.

The result is a system that turns a failing test into a diagnosed, patched and verified fix with no human in the loop. When the AI makes a claim about your tests, the system re-checks it by executing the code instead of believing the explanation.

The team

Meet the three agents

Each agent gets a short, focused prompt and is explicitly told what it must not do.

Diagnosis agent

Reads the broken code and the failing test output, then explains why it fails: the root cause, the faulty line and how confident it is.

DoesFinds the root cause
NeverWrites a fix

Fix agent

Takes the diagnosis and writes corrected code. The patch is saved to disk and a diff is printed so you can see exactly what changed.

DoesWrites the patch
NeverJudges its own fix

Mutation re-check agent

Once tests pass, it reviews every mutant your tests missed and decides whether it is harmless or a genuine hole in your test suite.

DoesVerifies the fix is real
NeverWrites code
Why three agents and not one? A narrow, focused prompt is more reliable than asking one model to diagnose, patch and grade its own work in a single step. When something goes wrong you also know which agent to look at.
Workflow

From failing test to verified fix

The orchestrator is the script that runs the whole sequence and passes context between agents.

1

Run the tests

The orchestrator runs pytest first to check whether the code is broken at all. If everything passes, it skips straight to verification.

2

Diagnose

The Diagnosis agent reads the code and the error output and returns the root cause, the faulty line and a confidence level.

3

Fix, then re-run

The Fix agent writes a patch, it is saved to disk, and the tests run again. If they still fail, the loop goes back to diagnosis with what was already tried, up to three times.

4

Mutate the fixed code

A custom mutation engine injects small fake bugs (mutants) and re-runs your tests against each. A mutant your tests catch is killed; one they miss has survived.

5

Judge every survivor

The re-check agent labels each survivor as an equivalent mutant or a real coverage gap. The system then runs the code itself to test that claim.

6

Final report

You get the fixed code, a verdict, recommended new tests, and a cost and time summary.

Key features

Built to be checked, not trusted

The features that matter most are the ones that stop the AI from being confidently wrong.

Specialised multi-agent design

Diagnosis, fixing and verification are separate agents with separate prompts, so each one stays focused.

Retry loop with memory

A failed fix is not the end. The system tries again, up to three times, using the earlier failed diagnosis as context.

Custom mutation engine

Built in-house because mutmut does not run on native Windows. It mutates comparisons, booleans, arithmetic and constants.

Self-verifying layer

Every “this mutant is harmless” claim is checked by running real code, with line-coverage and boundary-value tracing on the proof input.

Rate-limit resilient

Per-minute token limits trigger an automatic retry with back-off instead of a crash. Daily limits are reported clearly.

Browser debugger

Paste code, press run, watch the three stages light up, then copy or download the fixed file.

Mutation testing

How your tests get graded

Mutation testing deliberately breaks your code in small ways to see whether your tests notice.

killed

Tests caught it

A fake bug was injected and a test failed. Your coverage is doing its job.

survived

Tests missed it

The fake bug slipped through. It could be a real gap or a harmless change.

equivalent mutant

Looks different, acts the same

Behaves identically for every input, so no test could ever tell the difference.

real coverage gap

Behaves differently, untested

The change alters behaviour and nothing checks it. The report suggests a new test.

Line-coverage checkBefore any claim is trusted, the system confirms the proof input actually executed the mutated line.
Boundary-value checkIt then confirms the input’s runtime value sits in the narrow zone where the original and the mutant disagree.

Honest limits

What it cannot do yet

Knowing where a tool stops is part of using it well.

Needs a failing test

It only fixes bugs that a failing test points at. A bug with no test is invisible to it.

Limited mutation types

Mutants cover comparisons, booleans, arithmetic and constants. Mutable default arguments, closures, race conditions and security issues are out of scope.

No accuracy benchmark

It was tested on a small set of deliberate bugs, so there is no formal detection percentage to quote.

Depends on the model

Diagnosis quality follows the underlying model, which is why the re-check layer verifies by execution wherever it can.
